Prerequisites: You must have at least one webhook subscription configured in the Partner Developer Portal under Webhooks > Manage Subscriptions. Your receiving endpoint must be reachable over HTTPS with a valid TLS certificate. You should have access to your server logs to inspect raw request headers. Familiarity with HMAC-SHA256 signature verification is assumed.

  1. Locate the failed delivery in the Portal. Go to Webhooks > Delivery Logs. Each delivery attempt shows the event type, HTTP status your endpoint returned, the X-Brightline-Signature-256 header value sent, and a Delivery-ID. Filter by status Failed to find recent errors.
  2. Identify the failure category. Brightline classifies webhook authentication failures into three types: SIG_MISMATCH (your endpoint rejected the signature), ENDPOINT_AUTH_REJECTED (your server returned 401 or 403), and TLS_HANDSHAKE_FAILED (Brightline could not establish a secure connection).
  3. Resolve SIG_MISMATCH errors. Brightline signs each webhook payload using HMAC-SHA256 with the Webhook Signing Secret shown in Webhooks > Manage Subscriptions > [Subscription Name] > Security. To verify: (a) retrieve the raw request body as bytes before any parsing, (b) compute HMAC-SHA256(signingSecret, rawBody), (c) compare the result to the value in the X-Brightline-Signature-256 header using a constant-time comparison function. A mismatch almost always means the signing secret in your code is stale — copy the current value directly from the Portal and update your environment.
  4. Resolve ENDPOINT_AUTH_REJECTED errors. If your receiving endpoint requires its own authentication (e.g., a bearer token in the request or an IP allowlist), ensure Brightline's delivery IP ranges are permitted. Current egress IP ranges are listed in the Portal under Webhooks > Delivery Settings > Egress IPs. Update your allowlist and re-enable the subscription.
  5. Resolve TLS_HANDSHAKE_FAILED errors. Confirm your endpoint's TLS certificate is valid, not self-signed, and covers the exact hostname registered in the Portal. Brightline requires TLS 1.2 or higher. You can test connectivity using the Send Test Event button in the Portal, which returns a detailed error message for TLS failures.
  6. Rotate the signing secret if it was exposed. In the Portal, go to Webhooks > Manage Subscriptions > [Subscription Name] > Security > Rotate Secret. During rotation, Brightline sends both the old and new signatures for a 24-hour grace period so you can deploy your update without downtime. Accept either valid signature during that window.
  7. Trigger a backfill of missed events. Once authentication is restored, you can request redelivery of failed events. See How to Handle Pagination in Partner API Webhook Backfill Requests for step-by-step instructions on retrieving missed payloads in order.

Troubleshooting

Signature still mismatches after updating the secret: Confirm you are reading the raw request body. Middleware that parses JSON before your verification handler will alter the byte sequence and invalidate the signature. Disable body pre-parsing for the webhook route. Deliveries stop after secret rotation: The 24-hour dual-signature grace period begins at the moment you click Rotate Secret; if your deployment takes longer than 24 hours, the old signature will no longer be accepted — rotate again and deploy immediately. Test events succeed but live events fail: Check that your production endpoint URL matches the registered URL exactly, including trailing slashes. Repeated failures trigger subscription suspension: Brightline suspends a subscription after 50 consecutive failed deliveries; re-enable it from the Portal after fixing the underlying issue. For details on retry timing and backoff behavior, see Webhook Retry Policy Update – Partner API March 2026. If the issue is unresolved, submit a ticket via Help > Contact Partner Support and include the Delivery-ID values from the failed attempts.
