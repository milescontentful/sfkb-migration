How the Server Processes a Keyed Request

When Brightline's API receives a request with an Idempotency-Key header, it checks its deduplication store for a record matching that key plus the authenticated OAuth2 client ID. This means keys are namespaced per client—two different partners can use the same key string without conflict.

Possible Outcomes on Retry

First-request resultRetry behavior
Success (2xx)Returns the cached response body and original HTTP status. No action repeated.
Client error (4xx)Returns the same cached error. The request is not retried on the server.
Server error (5xx) or no response recordedRequest is treated as new and executed again.

Important Edge Cases

  • Mismatched request body: If you reuse a key but change the request payload, the API returns HTTP 409 with error code IDEMPOTENCY_KEY_CONFLICT. Always keep the body identical on retries.
  • Concurrent requests: Sending two requests with the same key simultaneously returns HTTP 409 with code IDEMPOTENCY_KEY_IN_FLIGHT. Wait for the first to complete before retrying.
  • Expired keys: Keys older than 72 hours are purged. A request with an expired key is treated as a brand-new operation.

Recommended Retry Strategy

  1. Generate a UUID v4 key before the first attempt.
  2. Retry only on network errors or 5xx responses.
  3. Use exponential back-off: 1 s, 2 s, 4 s, up to 5 attempts.
